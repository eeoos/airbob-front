# Frontend Browser Data Inventory

> Operational supplement to
> [`current-frontend-architecture.md`](./current-frontend-architecture.md).  
> Baseline: the 2026-09-01 contract-alignment worktree after the v2
> booking-payment owner switch, separate Detail/Availability reads, U13 editor
> command migration, U14 UI/catalog consolidation, U15 layout/token closure,
> and the U11 deterministic v2 browser matrix.

This inventory records data that can outlive a render, cross a navigation, or
appear in browser/QA artifacts. It contains no real credential, payment key,
reservation ID, listing ID, email, or member ID.

## Classification

| Class | Meaning | Examples |
| --------- | ---------------------------------------------------------- | ------------------------------------------------------------- |
| Public | Intended for browser delivery and safe to disclose | Route path, public image URL, browser API client key category |
| Internal | Application state that is not a credential | View mode, pagination, accommodation ID |
| Personal | Identifies or describes a user or their activity | Name, email, reservation dates, trip/host records |
| Sensitive | Authentication, payment, authorization, or replay material | Session cookie, payment key, reusable auth state |

Personal and Sensitive values must not be copied into committed fixtures,
documentation, screenshots, traces, videos, console logs, or generated reports.

### Browser history lifetime rule

`history.state` and URL query values belong to a browser history entry, not to a
React render. They can survive rerenders, back/forward traversal, and—in browser-
dependent cases—a reload or tab restoration. They disappear only when that
history entry is replaced or discarded, so “navigation-only” never means
“single-render” or “already validated.” Writers must keep fields minimal;
readers must validate every entry and explicitly consume transient commands
such as a one-time toast. Search, Detail/Review, Profile and the v2
booking-payment routes now use app-owned exact codecs. The flow and operation
references are deliberately credential-free; they can only locate an exact
same-owner storage record. A session cleanup can replace only the current entry
and cannot enumerate the browser Back stack, so every history reader still
enforces purpose/version, exact shape, route/resource, session and storage joins.

### Identity cleanup and generation rule

`src/app/providers/clearIdentityOwnedFrontendState.ts` composes transaction
route cleanup with booking-payment cleanup and injects those ports into the app
session owner. Generic login/external prechecks verify-delete only retired
prefixes and preserve v2 until the candidate subject is known. A pending,
already-scrubbed callback is joined to that candidate's exact journal before
identity publication; then candidate reconciliation publishes only `ready`,
`recovery-required`, or `recovery-unavailable`, never transaction data.

Explicit logout/revocation and a verified different-subject transition
verify-delete the full v2 namespace after QueryClient quarantine. Same-subject
recovery remains fenced until an exact workflow claims the current runtime
lease or verifies cleanup. Unknown/newer keys, malformed unknown versions,
invalid clocks, incomplete deletion and storage failures block identity
publication. The runtime lease is stored only inside exact journal/receipt
envelopes; it is never copied into URL/history, Query metadata, reducer state or
BroadcastChannel data. Workflow instances recheck captured subject/epoch and
route around every await so late continuations cannot recreate state.

### V2 persistence minimization

The active transaction uses three fixed v2 slots. The journal is intentionally
rich enough for exact quote/checkout/attempt recovery, while customer identity
and provider/backend prose stay outside it.

| Field group | Why it survives reload | Class | Decision |
| --------------------------------------------------------------------- | ------------------------------------------------------------------------ | ---------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `flowId`, owner, runtime lease, server intent and presentation counts | Join route/session and reconstruct the exact booking draft | Internal / Personal activity | Persist under the journal's hard and server-relative deadlines; never treat it as backend authorization. |
| Quote fields, including `quoteUid`, dates, `orderName`, amounts, currency and expiry | Render the explicit approval step and submit the exact quote | Personal activity / payment correlation | Persist exact mapped server values. The provider request preserves the validated bounded `orderName`; it is not trimmed or renamed. |
| Checkout method/resource/body, idempotency key and request fingerprint | Replay only the same checkout after an ambiguous response | Sensitive transaction correlation | Persist exact immutable request identity. A changed body, key, phase or flow fails closed. |
| Ready, payment-attempt and hold-release groups | Resume the current reservation hold and Toss request without creating a second reservation/attempt | Personal reservation/payment correlation | Persist only mapped allowlisted server fields and exact phase transitions. Ready supplies the Toss `orderName`; the joined attempt supplies `orderId` and amount. |
| `customerEmail`, `customerName` | Toss request only | Personal | Exclude from storage. Derive from the current authenticated viewer immediately before the gateway request and reject invalid/overlong input. |
| Callback credential tuple | Submit or resume the one exact confirm | Sensitive | Persist only in the dedicated 9-minute-capped slot after URL scrub and journal join; remove after verified receipt handoff. |
| Operation identity and safe observation | Poll and present the accepted operation across reload | Personal payment correlation | Persist only in the 24-hour receipt; exclude callback credential, status URL, raw failure/provider/backend message and direct PII. |

Retired v1 and unversioned objects are never migration input because current
code does not parse or consume their payloads.

## Cleanup events

| Event | Current cleanup | Target owner |
| ------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------ |
| Login or `/me` refresh to a different viewer | The session advances epoch, quarantines/cancels/clears the old QueryClient, then verify-deletes all identity-owned v2 and retired state before publishing the new subject. Old route/workflow continuations become stale. | App session + identity cleanup; backend cookie remains server authority. |
| Same-subject login or revalidation | Retired state is verify-deleted. A scrubbed fresh callback is first joined to the candidate's journal; candidate reconciliation then returns only clean/recovery status. Live same-owner v2 state is preserved and fences new booking/payment commands until exact recovery claims the current lease. | App candidate reconciliation + payment recovery fence. |
| Explicit logout, authentication revocation or verified different-subject transition | Local UI is fenced, the QueryClient generation is replaced, and full v2/retired cleanup is verified. No cookie is read or deleted; server logout remains revocation authority. | App session cleanup; non-PII BroadcastChannel is advisory only. |
| Quote abandoned or definitively rejected before a hold | The exact journal may be removed only from an allowlisted unheld phase/reason and only when no other v2 slot exists. | Booking transaction workflow + journal repository. |
| Complimentary checkout, server status drift or explicit hold release | After exact terminal projection succeeds, the pre-Accepted terminal journal is acknowledged and removed; navigation replaces to reservation detail. | Booking transaction workflow; Query publication is scoped and cannot create payment authority. |
| Backend confirm accepted (`202`) | A credential-free operation receipt with `observation:null` is written and read back first. Only then are callback credential and journal removed; a cleanup failure leaves the receipt authoritative and reports cleanup pending. | Recovery workflow + receipt repository. |
| `PENDING`, `PROCESSING` or `REQUIRES_REVIEW` operation | The safe observation replaces the receipt only under monotonic server evidence. Polling continues at the bounded backend delay; review keeps allowlisted reservation/operation identifiers visible and continues polling instead of clearing, declaring failure, or inventing support contact. | Payment Result controller + recovery workflow. |
| `SUCCEEDED` or `FAILED` operation | The terminal observation remains in the receipt until explicit user acknowledgment. Exact acknowledgment verify-clears the receipt before best-effort reservation cache invalidation and detail navigation. | Receipt repository is the terminal authority; cache/UI are projections. |
| Invalid success callback or provider failure callback | Native URL/Router state is scrubbed before children. An invalid or unjoined success tuple cannot confirm and does not delete an unrelated journal. The fail route is presentation-only and performs no storage, payment API or cache I/O. | Callback boundary + route adapters. |
| Ambiguous confirm or poll transport failure | The exact `confirm-submitting` journal/credential or operation receipt is retained. | Route/session change during Search/wishlist/detail/review/editor/payment | Commands recheck exact route and subject/epoch around awaits; disposal aborts reads, clears timers and suppresses stale publication. | Current migrated workflows and controllers. |
| Storage parse/version/owner failure | Known exact-v2 malformed, foreign or expired state is cleaned only where the repository proves it safe. Unknown/newer state, invalid clock, enumeration failure or unverified cleanup blocks; retired payloads remain opaque and prefix-delete only. | Platform storage driver + booking-payment repositories. |

## Retired compatibility and rollback

- The v1 checkout/callback repositories, direct reservation-create writer,
  legacy confirmation machine and checkout-ownership adapter are deleted. The
  only production payment flow is journal → callback credential → operation
  receipt through the current v2 workflows.
- The four retired prefixes remain purge-only security cleanup inputs. No
  reader, migration, marker hint or payload logging survives. A tab with only
  retired data starts a new v2 quote.
- The active Toss adapter uses the pinned official npm v2 SDK with `ANONYMOUS`,

## Change rule

A code change that adds a browser record, query exposure, URL callback field,
artifact type, or public environment value must update this inventory in the
same implementation unit. If purpose, minimal fields, subject, TTL, validation,
cleanup, or artifact policy is unknown, the new writer is not ready to ship.
